# Personal calendar service

`IGoogleCalendarService` follows the existing `BaseService` / package / Autofac structure.

```csharp
// Member-local calendar dates: inclusive start, exclusive end.
var startDate = new DateTime(2027, 1, 1);
var endDate = new DateTime(2028, 1, 1);
var entries = googleCalendarService.GetCalendarEntries(userId, startDate, endDate);
var ics = googleCalendarService.ConvertToICalendar(userId, entries);

// Or perform both steps:
var calendar = googleCalendarService.GenerateCalendar(userId, startDate, endDate);
```

`CalendarEntry` contains the local date, personal occupied houses, compact summary and plain-text combined prediction. It can also be used by a future website calendar or report. The member must have birth details and a saved calendar timezone (birth timezone is the default). Saved calculation, calculator, house and hemisphere preferences are read from the database, without relying on the requesting browser's session.

One all-day, transparent event is produced per date. The title is `9Star · 7.1.5`. When the chart returns a different afternoon house, `AfternoonDayHouse` records it and the description includes its combined prediction. The calendar fetches `NineStarKiService.GetPlannerData` in Year view and PersonalKi scope once per covered solar year, with one boundary retry when needed. The year energy and month rows provide year/month houses. Only overlapping months are expanded through Month view, passing `nineStarKiModel: yearlyPlanner.NineStarKiModel` so those calls reuse the profile instead of recalculating it. Daily and afternoon houses come from the month rows. Results are trimmed to the inclusive-start/exclusive-end Gregorian range, with contiguous coverage checked. The model's existing cycle-switch date also starts a fresh batch so a profile is not reused across a change in inversion state. The planner cache key includes the birth timezone and supplied profile's selected date, separating reused-profile batches from standalone calculations. A full profile is no longer calculated for each day. Local selected midnight (`DateTimeKind.Unspecified`) and the saved timezone are passed together, without first converting the date to UTC. Birth date, saved birth time and birth timezone are passed separately because the planner combines date and time itself. Solar-term days follow the existing planner's daily-row convention; these are all-day entries rather than timed transition events.

Any date range is supported. A January-to-December export still uses the existing Nine Star Ki calculation for year and month boundaries. No February boundary is hardcoded here. At midnight on a solar-year transition date, the exact transition may still be ahead while the previous year's all-day rows have already ended. When the Year planner returns a period ending before the requested cursor, the calendar retries at the returned end plus three days, matching existing planner forward navigation. The cursor stays on the original date, so the transition date is included. The retry is bounded; missing coverage still raises an error rather than skipping dates. For a Nine Star Ki year export, supply the dates determined by the existing astronomy service.

Website month data keeps its two-paragraph combined descriptions, now led by the daily influence and practical guidance, with a shorter year/month blend rather than extended background summaries. GenerateCalendar uses the same private planner/date batching with a feed-only description option, so it does not calculate or parse the website text first. No public service signature changes. The converter still exports exactly the entries supplied by its caller. The existing 729 combined descriptions are loaded through `K9.Globalisation.Dictionary.ResourceManager`, using your `Dictionary.resx` keys such as `_1_2_3` and the existing culture selection. No separate embedding rule or resource collection is added. Feed descriptions use 729 separate CalendarCombinedPrediction_Y_M_D resources in Predictions/Combined/en-gb/<year>/<month>/Y-M-D-calendar.txt. Each template has three IDEAL FOR bullets, a blank line, three BE MINDFUL OF bullets, a blank line and one concise blended paragraph. Shared CalendarIdealForHeading / CalendarBeMindfulOfHeading labels replace {0}/{1}; headings have no following blank line. A distinct afternoon energy appends its own labelled concise reading, separated by blank lines. The longer personal/global website resources are unchanged. Exported titles use PersonalCalendarEventSummaryFormat and the calendar display name reuses NineStarKiTitle. All display text belongs in Globalisation. Calendar text uses CRLF, RFC 5545 text escaping and UTF-8-aware 75-octet line folding. Event IDs remain stable for a member/date; the subscription URL should remain stable as well. The feed returns UTF-8 `text/calendar` content from the extensionless `/personal-calendar/feed?token=...` route. IIS can otherwise map a `.ics` URL to StaticFile before MVC receives it. The URL does not require a file extension for calendar subscription. After upgrading from the old `feed.ics` route, reload the chart and copy the link again; the token is unchanged, but any existing calendar subscription must use the new URL.

My Personal Chart now has a calendar panel beneath the current houses. It provides a Gregorian month grid using the existing energy images and `MediaService.BaseImagesPath`, month navigation, Today, selected-day combined text, help and a full-browser-window view. The expanded view closes with its button or Escape and keeps keyboard focus inside it. All fixed labels, messages, help and weekday names use strongly typed `Dictionary` properties backed by the Globalisation resource file; existing matching entries are reused. Only the calculated combined-prediction key uses a dynamic resource lookup. Date and month formatting use the request culture. The controls use the existing Bootstrap button helpers and the resource-labelled URL display template; dynamic day buttons clone a helper-rendered template. Navigation and Today occupy their natural width on the left. A flexible gap separates them from Copy calendar link, Expand and Help on the right. Copy and Expand are icon-only in narrow calendars, with resource-backed accessible labels and tooltips; the optional link-disable icon appears in the same action group. The toolbar wraps within the top area if space is insufficient. Expanded help text sits in the existing `.well` container inside its Bootstrap collapse wrapper, reusing shared rounded corners, equal padding and the white border in dark mode. Month requests use the existing panel displaySpinner/hideSpinner helpers rather than a Loading label; the initial request waits until the shared document-ready callbacks have registered those helpers. The current month remains visible until replacement cells are prepared; requests have a 30-second timeout, isolated AJAX handlers and guaranteed spinner cleanup on request errors and rendering exceptions. Rendering errors also report the exception to the browser console. Navigation tracks the requested month separately from the displayed month, so every rapid click advances or reverses the intended destination. Each click immediately invalidates and aborts the previous request and restarts a 400ms trailing debounce; clicks less than 400ms apart fetch only their final destination. A pause of 400ms starts a request, so later clicks must abort an already-started request rather than prevent it. Request-version checks prevent superseded responses or completion callbacks from rendering or clearing the current spinner. Navigation stays available while loading, subject to the 1900–2100 bounds; Today cancels pending navigation and requests the saved-timezone current month. Navigation clicks prevent default actions and do not bubble into ancestor page handlers. Day buttons have square proportions in both embedded and expanded views, with smaller dates positioned at the top left, energy artwork centred and the house triple at the bottom. When month data returns 409 (calendar unavailable), the existing birth-details/timezone message includes a helper-rendered My Account button linking explicitly to Account.MyAccount. Other errors and subsequent status updates hide this button. Month request failures log HTTP status, jQuery failure type and requested year/month to the console without exposing subscription tokens. The selected-day separator has 16px above and below it, with the heading top margin removed. All controls are at the top; the bottom subscription button and its spacing are removed. A standalone anti-forgery token preserves the POST checks, and the resource-labelled URL display remains available for manual copying after a link is requested. Empty status and trailing paragraph margins do not add space. The expanded desktop layout separates grid and details into columns; its horizontal separator returns in the stacked mobile view. Hover and keyboard-focus effects reuse the predictions calendar\'s 2px lift and 0 6px 16px shadow. The selected day uses the same primary-blue background, snow-white text and stronger shadow as predictions active days; today and selection keep that calendar\'s stacking order. Shadow overrides account for the general important button shadow in main/elements.less, and hover backgrounds use the current theme. Year and nine-year navigation remain future work.

`PersonalCalendarController` provides authenticated month data and anti-forgery-protected subscription/revocation POST actions. The anonymous feed requires a valid private token and checks the existing paid predictions access (or administrator status) on every request. UI access uses the existing predictions paywall inside the calendar panel body, so the Your Personal Calendar heading remains visible above the upgrade/login prompt. The protected calendar root stays inside the paywall wrapper, so unpaid users do not initialise calendar requests. Tokens are protected by ASP.NET MachineKey and stored in existing UserPreference records, so no database migration is required. The copied URL remains stable until revoked; disabling it makes the previous URL unusable. A new URL needs a new subscription in Google Calendar. The feed covers one local month behind today through twelve months ahead and reads saved calculation preferences each time. The subscriber's UI language is saved when the link is obtained. OAuth-based Google Calendar writes are not implemented.

Deployment: use a stable ASP.NET machine key across app restarts and any web-farm instances, as for forms authentication. Changing that key invalidates existing subscription links. The feed URL must be reachable from the internet; a localhost URL cannot be subscribed to by Google. Add the URL from Google Calendar on a computer via Other calendars > + > From URL. Do not log or share private subscription URLs.

The chart model now accepts an optional explicit calculator type. `NineStarKiService` passes its existing argument through before houses are calculated, allowing a calendar request to use the member's saved mode. Direct constructor callers that omit the argument retain existing behavior.

The calendar script is `Scripts/k9/personalCalendar.js`, included once through the existing main `~/Scripts/js` bundle wildcard. The personal-calendar partial has no separate script include. The script returns immediately on pages without its calendar and defers the initial request until the shared document-ready helpers have registered.

## Server behaviour during rapid navigation

Month GET requests use read-only session access, selected in `Application_PostMapRequestHandler` before `AcquireRequestState`. This preserves session identity (including impersonation) and culture while avoiding exclusive session locks between month requests. Subscription/revocation POST requests retain writable session access because preference updates refresh session values. Browser aborts alone do not stop synchronous server calculations: the month action passes the IIS client-disconnect cancellation token into a new calendar-service overload, which checks cancellation before work and between planner batches and while mapping daily rows. Existing three-argument callers, including ICS generation, keep their behaviour. Non-IIS hosts without disconnect notification fall back to no cancellation. An individual planner batch cannot be interrupted mid-call.

The reported cancelled requests around 30 seconds match the client timeout; session-lock queuing is a suspected cause, not confirmed by server tracing. Added a regression test asserting that an already-cancelled month does not read users or calculate profiles. No .NET Framework test runner is available here. Verify rapid double-clicks in both directions on IIS, including while a prior month is calculating: the destination must move twice, superseded requests may show Cancelled, and the final request must complete and clear the spinner. Read-only requests can still wait behind other page requests that hold writable session locks.

## Diagnosing slow responses

A reported browser timing showed 12.80 seconds Waiting for server versus roughly 1 millisecond downloading. This locates the delay before response delivery but does not distinguish server execution from server/session queuing. The remaining Month planner previously calculated a moon phase for every daily row, even though calendar entries never use it. Calendar calls now pass `includeMoonPhases: false` to skip planner-level/daily lunar enrichment, retaining the shared profile and astronomy energy batches. Other callers default to true. The planner now forwards the same option into every profile-creation path, so calendar profiles also skip their unused moon phase/lunar-day search. Standalone profile callers default to true, and the profile cache key includes the option. Timing before this change measured profile creation at 3.2–4.3 seconds and uncached daily astronomy batches at 1.4–2.1 seconds; these stages identify where time was spent, but do not prove how much each nested calculation contributes. The cache key includes the option, and regression coverage checks no planner lunar calls, unchanged energy rows and the existing default behaviour.

The initial local trace measured Year planner at 5,943ms and Month planner at 2,362ms, while user/preferences took 33ms. Detailed diagnostics now live inside `GetPlannerData`; duplicate outer calendar-service traces have been removed. The controller retains action entry, total time to entries and cancellation time.

In Visual Studio 2017, select Debug, rebuild and run with F5. Open View > Output and select Debug under Show output from. Reload one calendar month without additional navigation. Copy lines beginning `GetPlannerData` and `Personal calendar Month`. Each planner invocation has a short correlation ID, view and selected date so overlapping calls can be separated. Timings distinguish cache hit/miss, GetLichun, profile calculation or supplied-profile reuse, model/parent moon-phase setup, Year/Month boundaries, monthly/daily astronomy batches, row construction and final assembly. `stage` measures time since the previous marker; `total` measures the entire planner invocation. Row construction includes enumeration, energy mapping and view-model constructors (plus optional row moon phases for other callers); if an astronomy result is lazy, deferred work is measured there. Other planner views retain common setup/total timings.

All diagnostic timers and traces are inside `#if DEBUG`, with no timing work in Release builds. No birth details, user identifiers or private feed tokens are logged. Cache hits skip the calculation-stage markers; restart the application to compare a cold request with a repeat of the same month. If browser wait greatly exceeds action-entry-to-entries time, investigate work before the action or during response generation. ## Astronomy caching and remaining calendar optimisation

The owner applied the complete AstronomyService replacement through the local decrypted checkout and pushed the encrypted file. The supplied revision caches solstice instants by year/type, solar terms by year/longitude and solar-term arrays by adjusted Nine Star Ki year, using the existing cache helper with versioned ephemeris-path keys. Annual monthly rows use adjusted year/timezone/inversion, daily month batches use resolved boundaries/timezone, and Lichun retains the existing exact-instant year selection. The monthly-period cache now includes `invert`. Cached arrays added by this revision are cloned before returning. The numerical solver bodies remain unchanged. This description is grounded in the replacement provided to the owner; encrypted repository contents cannot be independently compared as plaintext here.

`CachableBase` now shares in-flight work for the same key across service instances, with a second cache lookup before computation. It removes only that completed/failed computation so future misses can retry, while unrelated keys remain independent. Existing expiration durations and shared-object behaviour remain. Cache eviction/removal does not stop work already running, and browser cancellation cannot interrupt an in-flight planner batch. Coalescing does not make different profile-date keys identical: complete profiles remain date-dependent.

Regression coverage adds profile lunar opt-out/default separation, energy equality and planner forwarding without a supplied profile, plus concurrent same-key cache reuse, independent keys, nested different-key reuse and failure retry. ### Independent selected-day lunar read

Detailed lunar-day calculation is performed only for the selected date, through GetLunarCalendarEntry and the same calendar batch builder. It is not repeated across the visible month. Its request/spinner/version are separate from month navigation; navigation, date changes and collapse invalidate and abort stale lunar reads. Both month and lunar-cycle GETs use read-only session access so lunar work cannot take an exclusive session lock ahead of navigation. The existing subscription/revocation POSTs retain writable session access.

Run `node tools/tests/test_personal_calendar_lunar.js` for the actual JavaScript request-handler harness. It covers main-loader completion before nested lunar loading, navigation during a pending lunar read, stale lunar response rejection and collapse to lightweight month data. C# tests cover lightweight phase calls for month entries and one detailed phase call for the selected date; these require the Windows solution and were not executed here.
